1CaptureA WAV at ≥ 44.1 kHz. Below that, Nyquist sits under the 18 kHz band and the screen reports insufficient data rather than guessing.
2MeasureWelch spectrum per 1 s window: share of energy above 18 kHz (ρA) and a CFAR-detected narrowband peak above 15 kHz with its modulation sidebands (ρB).
3DecideR = √(ρA × ρB) — both signatures must be present. ≥ 0.33 suspicious, ≥ 0.66 high risk. The worst window decides.
4GateVerdict × action class → allow, confirm or block, under the policy you set. Nothing here reads or reconstructs a command.

Principles

Critical actions should never execute silently. Even on a clear verdict, an unlock or payment deserves a confirmation — the screen is not a guarantee.

“Could not check” is not “safe”. A 16 kHz capture returns insufficient data; treat sensitive actions from it as unverified.

Defence in depth. Combine with speaker verification, liveness and rate limits. The gate is one signal.

API

The same engine over HTTP · stateless · nothing stored server-side
POST/api/scan
Multipart file (WAV), optional window, hop. Returns verdict, risk, per-detector evidence, engine thresholds, PSD, spectrogram grid, waveform, window timeline and a capture-rate note.
curl -F file=@clip.wav -F window=1.0 \ http://127.0.0.1:8000/api/scan
POST/api/gate
Multipart file, action = routine | sensitive | critical, optional command and policy (JSON matrix, as saved in Gate policies). Returns allow, confirm or block with the reason.
curl -F file=@cmd.wav -F action=critical \ -F command="unlock the door" \ -F policy=@policy.json \ http://127.0.0.1:8000/api/gate
